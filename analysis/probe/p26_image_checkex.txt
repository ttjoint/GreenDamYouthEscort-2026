# CImage.dll：CHECKEX 家族与 OpenCV 调用链（查证，非新逆向）

方法：PE-HDR（导出表 + 导入表）+ DISASM（capstone 精确反汇编 .text，
收集真实 call 指令，做 3 层 BFS）

## 1. 起因

账本 `IMG07`（`00b-FACTS.md`）记「CImage.dll 用 OpenCV 轮廓/形态学/霍夫线全套」，
状态 `CLOSED`。但该条证据只到**导入表**层面——「导入了」不等于「调用了」。
本轮查证这两者的差别。

## 7. 3 层 BFS：15 个 CHECK* 都能到达 OpenCV

| 函数 | 可达的 OpenCV |
|---|---|
| CAPSCREEN | 15 个（含 cvLoadImage 之外的全部） |
| CHECKEX2 | 15 个 |
| CHECKEX3/4/4DIR/5 | 15 个 |
| CHECKEX6/6x/7/7x/8x/11x/13x | **17 个**（多 cvLoadImage + cvResize） |
| CHECKEX10x/12x | 16 个 |

**因此 `IMG07` 的 `CLOSED` 成立**，但证据链应补上"调用可达"这一层，
而不是停在导入表。

## 8. 新发现的问题（未解决）

1. **17 个 CHECKEX 各自的语义未知**。账本只描述了 `CHECKEX2`
   （首参必须 0x7ab7、否则 Sleep(10000)+返回 100）。
   其余 16 个的参数契约、返回码、判定逻辑**完全未逆向**。

2. **CAPSCREEN 1353 条指令**（4,224 字节）——它内部直接或间接用到了
   15 个 OpenCV 函数，但抓屏→OpenCV 的完整数据流未追踪。

3. **CHECKEX8x / CHECKEX13x 各 1,363 / 845 条指令**，规模与 CAPSCREEN
   同量级，说明图像判定逻辑的**主体在这两个函数里**，而非 CHECKEX2。

## 9. 对 M4 实现的影响

现有 `src/green_dam/imaging.py` 只复刻了 `0x10008e20`（宽高比）与
`0x10008e70`（高亮度直方图）两个**算术函数**。这两个函数确实存在，
但**不是 CHECKEX 家族的主判定路径**。

真正的主判定在 `CHECKEX8x` / `CHECKEX13x` / `CAPSCREEN` 里，走 OpenCV
轮廓分析。**未逆向，不可复刻。**

因此 M4 的状态应明确为：**两个辅助判据已复刻，主判定路径未复刻**。
`docs/image-layer.md` §5 已说明 Haar 未做，但未说明**轮廓路径也未做**——
本轮查证补上这一点。
