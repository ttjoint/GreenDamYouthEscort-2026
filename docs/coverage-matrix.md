# 覆盖矩阵：扩展 / 代理 / 防火墙各能看见什么

本文回答一个具体问题：**用浏览器扩展做网络检测，是否就不需要网关（代理）模块了？**

答案是**不能**，但理由比"功能不同"更具体。下面逐项列出三层的可见范围、
重叠区、以及各自的盲区。所有结论都可以用文中的命令复现。

---

## 1. 三层机制，三种可见性

| 层 | 代码 | 看见什么 | 覆盖谁 | 需要什么 |
|---|---|---|---|---|
| **防火墙** | `host/firewall.py` | **IP 地址**（不含域名） | 操作系统层，**所有应用** | 管理员 |
| **代理** | `host/proxy/` | HTTP 明文：**域名 + 完整响应体** | 配置了代理的应用 | 管理员（或系统代理） |
| **扩展** | `host/extension/` | **解密后的 DOM** | 装了扩展的浏览器 | 浏览器策略 |

三者的可见性是**正交**的，不是递进的：

- 防火墙覆盖最广（所有应用），但看不见内容，甚至看不见域名。
- 代理看得见内容，但只覆盖"愿意走代理"的应用。
- 扩展看得最清楚（DOM），但只覆盖装了扩展的浏览器。

---

## 2. 扩展的盲区（实测）

### 2.1 扩展只覆盖 3 个浏览器

```bash
python -c "from host.browsers import detect; print([b.display_name for b in detect()])"
# ['Google Chrome', 'Microsoft Edge', 'Mozilla Firefox', 'Internet Explorer']
```

`Internet Explorer` 的 `configurable=False`（`host/browsers.py`），
即**策略不可配置**，扩展装不上去。实际可覆盖的是 Chrome / Edge / Firefox。

### 2.2 扩展完全看不见非浏览器流量

这是最要紧的一条。扩展运行在浏览器沙箱里，只能看浏览器渲染的页面。以下全部看不见：

| 流量类型 | 例子 | 扩展能看见吗 |
|---|---|---|
| 游戏客户端 | Steam、Epic、原神 | ❌ |
| 即时通讯 | QQ、微信桌面版、Discord、Telegram | ❌ |
| 内嵌 WebView | 微信内置浏览器、QQ 内置、Electron 应用 | ❌ |
| 下载工具 | IDM、迅雷、BT 客户端 | ❌ |
| 云盘同步 | OneDrive、百度网盘、坚果云 | ❌ |
| 未装扩展的浏览器 | 绿色版 Chrome、便携版 Firefox、新装的浏览器 | ❌ |
| 命令行工具 | curl、wget、pip、npm | ❌ |

**代理能覆盖其中的一部分**：走系统代理（WinINET）的应用包括多数 .NET 程序、
Electron 应用（默认读系统代理）、部分游戏启动器。
**防火墙能覆盖全部**，但只能按 IP 拦，且 IP 会变。

### 2.3 扩展主动跳过特定元素

`host/extension/__init__.py::SKIP_TAGS` 明确列出**永不判定的容器**：

```python
SKIP_TAGS = (
    "nav", "header", "footer", "script", "style", "noscript",
    "form", "button", "input", "select", "textarea",
    "svg", "canvas", "video", "audio", "iframe",
)
```

其中 **`video`、`canvas`、`iframe`** 是内容盲区：

- **`video`**：视频帧不做判定。扩展只对 `<img>` 的 URL 做分类（`content.js`
  发送图片字节到评分服务）。视频里出现什么，扩展完全不知道。
- **`canvas`**：WebGL / Canvas 渲染的内容（网页游戏、部分阅读器、图片查看器）
  不在 DOM 文本里，`querySelectorAll` 取不到。
- **`iframe`**：容器本身不判定。但清单里 `all_frames: True`
  （`host/extension/__init__.py`），所以 **iframe 内部的页面会被单独注入
  content script 并单独判定**——这一条是覆盖的，只是容器自身不作为文本判定对象。

这条区分很重要：`iframe` 在 `SKIP_TAGS` 里**不代表不覆盖**，
而是"不把 iframe 标签自身的文本当内容"。实际内容由 `all_frames` 处理。

### 2.4 扩展看不见导航请求

扩展的清单权限只有：

```json
"permissions": ["storage", "activeTab"]
```

**没有 `webRequest`、没有 `tabs`、没有 `webNavigation`。** 这是刻意的
（`docs/host-layer.md` §2.6，以及 `host/tests/test_extension.py::NoRemoteCodeTest`）：

- 扩展**不能**在请求发出前拦下它，只能等页面加载后隐藏元素。
- 扩展**不能**阻止导航到某个 URL，只能事后隐藏。
- 这意味着：一个纯图片站，扩展会在图片加载完之后才隐藏它——
  **图片字节已经下载到本机**。

代理不同：它在**连接上游之前**就能拒绝，字节根本不进入本机。

| | 扩展 | 代理 |
|---|---|---|
| 阻止请求发出 | ❌ | ✅ |
| 阻止字节进入本机 | ❌ | ✅ |
| 隐藏已加载的内容 | ✅ | — |
| 覆盖非浏览器 | ❌ | 部分 |

### 2.5 扩展看不见 HTTPS 的原始流量

扩展拿到的是**解密后的 DOM**，这是它的优点（不需要 CA），也是它的边界：
它看不到 TLS 层的 SNI、证书、连接目标。所以它无法回答
"这个页面从哪些第三方域名加载了资源"这类问题。

代理（即使不解密）能看见 SNI 和 CONNECT 目标。

## 3. 重叠区与缺口

```
                    防火墙        代理         扩展
                    (IP)        (HTTP明文)    (DOM)
                      │            │            │
所有应用 ─────────────┼────────────┘            │
                      │                         │
遵守系统代理的应用 ────┼─────────────┼───────────┘
                      │             │
Chrome/Edge/Firefox ──┼─────────────┼───────────┼──── 全可见
                      │             │           │
页面文本 ──────────────┼─────────────┼───────────┼──── 全可见
HTTP 响应体 ───────────┼─────────────┼───────────┤
HTTPS 响应体 ──────────┼─────────────┤           ├──── 仅扩展
视频/Canvas ───────────┼─────────────┤           ┤   ← 全部盲区
非浏览器流量 ───────────┼─────────────┤           ┤
```

**只有扩展能做的**：HTTPS 页面内容（无 CA）。
**只有代理能做的**：阻止字节进入本机、看见非浏览器应用的 HTTP 内容。
**只有防火墙能做的**：覆盖完全不走代理的应用（但只能按 IP）。

---

## 4. 结论：不能去掉代理

### 4.1 去掉代理会丢掉什么

| 能力 | 去掉代理后 |
|---|---|
| 阻止字节进入本机 | ❌ 丢失。所有被拦内容都已下载，只是被隐藏 |
| 非浏览器应用的 HTTP 内容过滤 | ❌ 丢失 |
| HTTPS 的 SNI / 连接目标可见性 | ❌ 丢失（扩展看不到） |
| 未装扩展的浏览器 | ❌ 丢失 |
| 拦截页（说明为什么被拦） | ❌ 丢失（扩展只能就地隐藏元素） |

### 4.2 但代理也确实不是"网关"

你提到"网关相关内容"。需要澄清：**本项目没有网关模块，也不应该有。**

- `host/proxy/` 是**显式代理**（explicit proxy），不是透明网关。
  它只处理"客户端主动把请求发给它"的流量。
- 真正的网关需要 ARP 欺骗、路由重定向或 WFP 驱动，那会拦截**整台机器**
  的所有流量，包括家长的网银和公司 VPN——这正是本项目拒绝 MITM 的同一条理由
  （`docs/architecture.md` §M2，理由 1：范围）。

所以准确的说法是：**代理不是网关，它是"愿意走代理的应用"的检查点。**
它和扩展是互补的两个检查点，覆盖不同的应用集合。

### 4.3 三层的实际分工（建议）

| 场景 | 谁负责 |
|---|---|
| 孩子在 Chrome 里看网页 | 扩展（DOM 判定）+ 代理（阻止字节） |
| 孩子在 QQ 内置浏览器里看 | 代理（如果 QQ 走系统代理） |
| 孩子在 Steam 里看社区 | **都覆盖不到**（除非防火墙按 IP 拦） |
| 孩子用命令行 curl 下载 | 代理（如果配了环境变量）或**覆盖不到** |
| 页面里嵌入的视频 | **都覆盖不到**（`SKIP_TAGS` 含 `video`） |

## 5. 对路线图的影响

这个分析**不改变实施顺序**，但改变阶段 1 的理由强度：

`docs/roadmap.md` 阶段 1 是"浏览器代理策略 + 优雅关闭"。原本的理由是
"没策略就没人用代理"。现在的理由更硬：

1. **代理是唯一能阻止字节进入本机的机制。** 只有扩展的话，
   产品变成"下载完之后藏起来"，这在法律和伦理上都比"不下载"弱得多。
2. **代理是唯一覆盖非浏览器应用的机制**（部分）。
3. 但**代理不覆盖视频和 Canvas**，这是已知缺口，应写进验收文档而不是假装没有。

### 5.1 需要补充到验收清单的缺口

阶段 5（全系统验收）应显式测试并记录以下**已知不覆盖**：

| 缺口 | 验收时的处理 |
|---|---|
| 视频内容 | 记录为已知限制；可选：后续用 `video` 截图送评分服务 |
| Canvas / WebGL | 记录为已知限制 |
| Steam / Discord 等非浏览器应用 | 记录；防火墙按 IP 拦是唯一手段 |
| 未装扩展的浏览器 | 记录；安装程序应报告检测到但未覆盖的浏览器 |

**"不覆盖"必须被写下来**，否则家长会以为装了就全防住了。
这与项目一贯的"没查 ≠ 干净"是同一条规则。

---

## 6. 一个可选的方向（不建议现在做）

如果确实需要覆盖视频，有两条路：

1. **扩展截取 `<video>` 帧送评分服务**：技术上可行（`canvas.drawImage(video)`），
   但每秒数帧的推理成本很高，且需要新增 `webRequest` 之外的权限。
2. **代理层做视频解码**：代价极高，且 HTTPS 视频解不了。

两者都超出当前阶段。**先不做，但记录在这里**，因为它是"扩展 vs 代理"讨论中
唯一真正需要新机制的地方。
