# 原始 HNC 引擎的过滤库：实测有效

**结论先行**：`SentenceObj.dll` 的**过滤**功能完全可用，共 **4,693 条**
打分记录，已全部导出到 `data/hnc-falun-filter.json`。

**这条结论修正了 `hnc-engine-probe.md` 早前的判断。** 那份文档说
「引擎能调但给不出结果，所以不能当后端用」——**那句话只对「句类分析」
成立，对「过滤」不成立**。两者走的是两条互不相干的路。

## 1. 两条路的分岔

```
句类分析    CSentenceObj::Ini   →  要 12 个 .lib（包里一个都没有）→ 死路 ❌
词条过滤    CreateHncTextGroup  →  只要 FalunWord.lib（包里有）    → 活路 ✅
```

`GetWordFanDong` / `GetWordHongHei` 是 **`CFWordLib` 的成员函数**，
不碰 `CSentenceObj`，所以那 12 个缺失文件跟它们毫无关系。

我之前的错误是把两者混为一谈：看到 `Ini` 失败、`GetSentenceALC` 返回 7，
就笼统地判定「引擎没用」。**实际上大部分导出函数都不走 `Ini`。**

## 2. 反汇编依据

`?GetWordFanDong@CFWordLib@@QAEHH@Z` @ **0x2d80**：

```asm
8b 44 24 04        mov  eax, [esp+4]          ; eax = idx
3b 81 2c 01 00 00  cmp  eax, [ecx+0x12c]      ; cmp idx, count
7d 14              jge  ret0                  ; idx >= count -> 0
85 c0              test eax, eax
7c 10              jl   ret0                  ; idx < 0      -> 0
8b 89 28 01 00 00  mov  ecx, [ecx+0x128]      ; ecx = 打分表
c1 e0 04           shl  eax, 4                ; idx * 16（每条 16 字节）
8b 44 01 08        mov  eax, [ecx+eax+8]      ; ★ +8 = 反动度
c2 04 00           ret  4
ret0:
33 c0              xor  eax, eax
c2 04 00           ret  4
```

`?GetWordHongHei@...` @ **0x2d50** 与它逐字节相同，只有字段偏移从
`+8` 换成 `+0xc`（= `+12`，红黑度）。

**纯内存查表，完全不做文件 I/O。** 这就是它能用的根本原因。

## 3. 对象里的四张表

`LoadLib`（@0x22d0）从 `FalunWord.lib` 读入四张表：

| 字段 | 内容 | 条目数 | 每条字节 |
|---|---|---|---|
| `[G+0x128]` | **打分表**（`+8` 反动度、`+12` 红黑度） | `[G+0x12c]` = 4,693 | 16 |
| `[G+0x134]` | **词条文本**（UTF-16 连续字符流） | `[G+0x138]` = 36,943 | 2 |
| `[G+0x140]` | 字符节点表（trie 节点） | `[G+0x144]` = 272,920 | 16 |
| `[G+0x148]` | 附加表 | `[G+0x13c]` | — |

`G` = `CreateHncTextGroup()` 返回值 `- 0x124`（主对象）。

### 关键结构：打分表怎么找到词

```asm
; LoadLib 读表（0x2410 附近）
57                    push edi            ; fp
68 ff ff 00 00        push 0xffff         ; 分隔
8d 96 4c 01 00 00     lea  edx,[esi+0x14c]
6a 10                 push 16             ; 每条 16 字节
52                    push edx
e8 ...                call fscanf
```

- `u32[0]`：**文本表的字符下标**（不是指针，也不是字节偏移）。
  实测取值 `0..36941`，上限恰为 `[G+0x138]` = 36,943。
- `u32[1]`：未初始化堆填充（`0xCDCDCDxx`），**无意义，别读**。
- `u32[2]`：反动度。
- `u32[3]`：红黑度。

### 词条长度 = 与下一条的位置差

**这是最容易踩的坑。** 文本表是一整条连续字符流，条目之间**没有**
NUL 或任何终止符。正确切法是：

```python
end = offsets[k + 1] if k + 1 < len(offsets) else text_len
word = text[offsets[k]:end]
```

按「遇到非汉字就停」去切会得到粘连的乱码（我第一版就错了）。

## 5. 交叉校验

导出工具做了双向验证：

1. 从**内存表**直接读 4,693 条 `(反动度, 红黑度)`。
2. 对每一条调用 **`GetWordFanDong(i)` / `GetWordHongHei(i)`**。
3. 断言两者完全相等。

```
交叉校验：4693 条 GetWordFanDong/GetWordHongHei 与内存表一致
```

**4,693 条全部通过。** 这不是「读到了点东西」，是「函数真的在工作」。

## 6. 复现方法

```bash
# 必须 32 位 Python 2.7（DLL 是 PE32 x86）
D:\Python27\python.exe -u tools/dump_falun_filter.py
```

必要条件（和 `hnc-engine-probe.md` §0 同一套）：

1. 32 位进程（64 位加载 PE32 会直接拒绝）。
2. `SentenceObj.dll` + `HNCLIB\FalunWord.lib` 拷到**纯 ASCII 路径**
   （中文路径会让 `LoadLibraryA` 失败）。
3. `chdir` 到该目录，用**裸文件名** `CDLL("SentenceObj.dll")`。
4. `CreateHncTextGroup` 的参数**必须以 `\` 结尾**。
5. `this` 传**主对象** `global`（`g - 0x124`），不是子对象 `g`。
6. 函数地址用 **`dll._handle + RVA`**，不能硬编码 `0x10000000`。
7. 手写 thunk 调 `ret N` 函数（ctypes 会重复弹栈）。

## 7. 这改变了什么

### 对项目定位的影响

之前我写道：「原始引擎的证据价值在输出格式和模块划分，不在标准答案」。
**这句话现在要改**：对**过滤**这一块，原始引擎给的就是标准答案——
4,693 条带分级的真实词库，可以直接拿来跟我们的实现对照。

### 与现有 `semantic.py` 的关系

项目里已有 `LegacySemanticMatcher`（`data/legacy-imported/falun-terms.json`，
10,182 条，等级 0..7）。现在有了原始引擎的 4,693 条权威数据，
**可以做一次真正的差分对照**：

- 哪些词我们多出来了（可疑：可能是误解析）
- 哪些词我们漏了（危险：漏检）
- 等级映射对不对得上

这是此前做不到的验证。

### 仍然不能做的

句类分析依然走不通（12 个 `.lib` 缺失）。`GetSentenceALC` 依然返回 7。
**过滤能用 ≠ 分析能用**，这一点没有变。
