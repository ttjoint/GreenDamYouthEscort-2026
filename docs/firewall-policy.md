# 防火墙策略：规则管理、按域名/按 IP、时间控制

本文回答两个问题：

1. 防火墙是否需要系统提供规则导入、用户编辑/查看/增删，按域名或按 IP 拦截？
2. 上网时间管理是否要求防火墙能按系统时间做**全网拦截**？

结论先给：**第一个要，但按域名和按 IP 要分开对待；第二个不要用防火墙做。**

理由如下。所有"现状"都可以用文中命令复现。

---

## 1. 防火墙能做什么，不能做什么

`host/firewall.py` 生成 `netsh advfirewall` 规则。Windows 防火墙的规则条件集合是固定的：

| 条件 | Windows 防火墙支持 | 本项目用到 |
|---|---|---|
| 程序路径 | ✅ | ❌（未用） |
| 端口 / 协议 | ✅ | ❌（未用） |
| **本地/远程 IP（含 CIDR）** | ✅ | ✅ |
| 用户 / 服务 | ✅ | ❌（未用） |
| 接口类型 | ✅ | ❌（未用） |
| **域名 / 主机名** | ❌ **不支持** | — |
| **时间范围** | ❌ **不支持** | — |

两条"不支持"是本文的核心，因为它们决定了下面所有设计。

## 2. 按 IP 拦截：现在能用，但曾有一个 bug

### 2.1 现状（已修）

`build_add_rules` 接受单地址和 **CIDR 网段**：

```bash
python -c "
from host.firewall import build_add_rules
for a in ('1.2.3.4','10.0.0.0/8','0.0.0.0/0'):
    p = build_add_rules([a]); print(a, '->', len(p.rules), 'rule(s)')
"
# 1.2.3.4      -> 1 rule(s)
# 10.0.0.0/8   -> 1 rule(s)
# 0.0.0.0/0    -> 1 rule(s)
```

### 2.2 曾经的问题

`is_address` 原先只用 `ipaddress.ip_address`，**拒绝一切带前缀的输入**。
后果：任何 CIDR 都被静默丢进 `rejected`。

```python
build_add_rules(["10.0.0.0/8"])
# 修复前: FirewallPlan(rules=(), rejected=('10.0.0.0/8',))   ← 一条规则都没有
# 修复后: FirewallPlan(rules=(...), rejected=())              ← 一条网段规则
```

这个 bug 的形态值得记下来：**它不会报错，只会"什么都没拦"**。
调用方看到 `rejected` 里有内容，但很容易把它当成"用户输入有问题"而不是
"我们的校验器太窄"。这正是本项目反复强调的那类失败。

修复后 `0.0.0.0/0` 可用，这是时间控制方案（§4）的前提。

### 2.3 按 IP 的固有限制

`host/firewall.py` 的模块注释已经写明，这里重申：

> `netsh` accepts no host names, and Windows Firewall resolves nothing at
> rule-creation time.

所以：

- **按 IP 拦是"当下快照"**。一个域名今天解析到 `1.2.3.4`，明天换到 `5.6.7.8`，
  规则就失效了。
- **CDN 让这件事更糟**。同一个域名在不同时间、不同地区解析到不同地址，
  想拦一个站点可能要拦几十个 IP，且随时变化。
- **动态 IP 的对手**：成人站点大量使用快速轮换的域名和 IP。
  这正是 `docs/architecture.md` §M2 说"维护一个列表需要网络更新，
  而本产品没有网络"的地方。

**结论**：按 IP 拦**只能作为辅助**，用于两类场景：

1. 已知固定的地址（企业内部服务、特定服务器）；
2. **全网/网段级**策略（`0.0.0.0/0`、允许列表之外的地址），
   这类场景 IP 粒度反而是正确粒度。

**不能**把"按 IP 拦域名"当成内容过滤手段。内容过滤靠扩展（DOM）和代理（HTTP 体）。

## 3. 按域名拦截：防火墙做不到，应该由代理做

### 3.1 为什么不在防火墙上做

Windows 防火墙没有域名条件。想"按域名拦"，只有三条路：

| 方案 | 做法 | 问题 |
|---|---|---|
| 解析后写 IP 规则 | 定期 `nslookup` 再 `build_add_rules` | 需要网络（违反离线约束）；IP 变化即失效；CDN 下几乎无效 |
| 改 `hosts` 文件 | 把域名指向 `0.0.0.0` | 只影响遵守 hosts 的应用；HTTPS 下 SNI 仍暴露；可被孩子改回 |
| **走代理** | 浏览器/应用把请求发给本地代理，代理按域名判定 | **需要应用愿意走代理** |

### 3.2 代理是域名拦截的正确位置

`host/proxy/` 已经在做这件事，而且比防火墙强：

| | 防火墙（按 IP） | 代理（按域名） |
|---|---|---|
| 看见域名 | ❌ | ✅ |
| 看见 SNI | ❌ | ✅ |
| 看见响应体 | ❌ | ✅（HTTP） |
| 阻止字节进入本机 | ✅ | ✅ |
| 覆盖非代理应用 | ✅ | ❌ |

**所以三层不是替代关系**（详见 `docs/coverage-matrix.md`）：

- 防火墙：覆盖广、粒度粗（IP）、看不见内容。
- 代理：粒度细（域名 + 内容）、但只覆盖走代理的应用。
- 扩展：粒度最细（DOM）、但只覆盖三个浏览器。

### 3.3 用户编辑域名列表 = 编辑什么

如果要做"用户按域名增删"，**编辑的对象是代理的域名列表，不是防火墙规则**。

`host/namelists.py`（名单 A/B/C/D）已经承载了名单语义。域名拦截应接在这里，
而不是新造一套防火墙域名表——那会得到两套不一致的名单。

## 4. 时间控制：不要用防火墙做

### 4.1 为什么不用防火墙

Windows 防火墙**没有时间条件**。想按时间开关防火墙规则，只有：

| 方案 | 做法 | 问题 |
|---|---|---|
| 定时任务切换规则 | `schtasks` 在边界时刻 `netsh add/delete` | 边界时刻有窗口期；服务没起来就不切换；规则残留 |
| 服务自己判断 | 服务按 `schedule.py` 决定是否放行 | ✅ **推荐** |
| 禁用网卡 | `netsh interface set interface disabled` | 粗暴；会把家长的连接也断掉 |

### 4.2 推荐方案：判定链短路，不是防火墙切换

`src/green_dam/filter.py` 已经实现了正确的位置：

```python
if (self.schedule is not None and when is not None
        and self.legacy is not None):
    enabled = self.legacy.get(24) != 0
    if not self.schedule.is_allowed_at(when, enabled=enabled):
        self._record_gate("outside_allowed_hours", source="schedule")
        return Assessment(action=None, source="schedule",
                          reason="outside_allowed_hours")
```

**时间检查在判定链的最前面，短路掉后面所有"查什么"的阶段。**
理由是 `filter.py` 注释里写的：

> the schedule is about *when*, so it short-circuits the *what* stages.

这个位置比防火墙好，因为：

1. **统一**。代理、扩展、图像判定都走同一个入口，时间规则只写一次。
2. **可测**。`WeeklyGrid` 是纯数据 + 注入时钟，38 项测试不依赖真实时间。
3. **可解释**。被拦时日志记 `outside_allowed_hours`，家长看得懂。

### 4.3 但"全网拦截"需要防火墙配合

上面只拦**走代理的应用**。如果要求"时间到了，整台机器断网"，
代理做不到（不走代理的应用不受影响）。

这时需要防火墙，而且需要 `0.0.0.0/0`：

```python
build_add_rules(["0.0.0.0/0"])   # 一条规则，阻断全部出站
```

**这正是 §2.2 那个 bug 会造成的后果**：修复前，这条调用返回空计划，
"全网断网"静默变成"什么都没发生"。修复后它可用。

### 4.4 两种时间控制，需要分别决策

| 类型 | 机制 | 覆盖范围 | 状态 |
|---|---|---|---|
| **软时间控制** | `filter.check_request` 短路 | 走代理的应用 | **DONE**（引擎侧） |
| **硬时间控制** | 防火墙 `0.0.0.0/0` 增删 | 全部网络 | **未接线** |

软控制已实现但**没有接线**（`host/engine.py` 从不构造 `schedule`，
代理也从不传 `when=`）。硬控制连设计都还没定。

### 4.5 硬时间控制的三个必须先想清楚的问题

在实现"按时间全网断网"之前，这三件事必须有答案：

**1. 边界时刻的窗口期。**
定时任务在 `20:00` 执行，如果任务延迟 30 秒，那 30 秒是通的。
用服务内部定时器（不是 `schtasks`）可以缩短，但不能消除。
→ 决策：接受窗口期，还是用"提前 5 分钟预警"（原厂做法）？

**2. 失败模式：规则加上了但没删掉。**
服务在断网期间崩溃，重启后没恢复规则 → **机器永久断网**。
这是"保护软件把电脑搞坏"的最严重形态。
→ 必须：规则带固定前缀（`GreenDam2026-`，已有）+ 启动时清理孤儿规则。

**3. 孩子改系统时钟绕过。**
原厂用 10 个硬编码 NTP 服务器同步时钟（`analysis/00b-FACTS.md` SCH04，
`0x68228..0x682b4`）防这一手。

**但本项目承诺零网络依赖**（`docs/host-layer.md` §2.12），
且那 10 个服务器是 2009 年的地址，今天大概率已失效。

→ 替代方案（按推荐顺序）：

| 方案 | 做法 | 是否需要网络 |
|---|---|---|
| **A. 收回改时钟权限** | `SeSystemtimePrivilege` 只给 Administrators（组策略/`secedit`） | ❌ |
| **B. 单调时钟锚定** | 服务启动时记 `(wall, monotonic)`，用单调时钟推算 | ❌ |
| **C. 检测时钟跳变** | 发现系统时间倒退/跳跃就记录告警 | ❌ |
| D. NTP 同步 | 原厂做法 | ✅ **与离线约束冲突** |

**推荐 A + B**：A 直接消除攻击面（孩子账户本来就不该有改时钟权限），
B 兜住服务运行期间的跳变。两者都不需要网络。

这也意味着 **J8（NTP 防改时钟）应该从 MISSING 改为"不做，用 A+B 替代"**，
理由与拒绝 MITM 相同：为了实现一个功能而引入网络依赖，代价大于收益。

## 5. 规则管理：导入、查看、增删

### 5.1 现状

| 能力 | 状态 | 位置 |
|---|---|---|
| 生成规则（数据） | **DONE** | `build_add_rules` |
| 生成 netsh 命令 | **DONE** | `build_add_rules_command` |
| 删除命令（按组） | **DONE** | `build_remove_rules` |
| 查看命令 | **DONE** | `build_show_rules` |
| 执行（真的调 netsh） | **TODO** | 属安装程序 |
| 导入/导出规则文件 | **TODO** | — |
| GUI 增删 | **TODO** | 控制台只读 |

### 5.2 导入/导出应该是什么格式

不建议自定义二进制格式。两个候选：

| 格式 | 优点 | 缺点 |
|---|---|---|
| **JSON（本项目格式）** | 与 `namelists.py` 一致；可读；可 diff | 不是 Windows 标准 |
| `.wfw`（Windows 防火墙导出） | 系统原生 | 含大量无关字段；难验证 |

**建议 JSON**，且与名单文件同构：

```json
{
  "version": 1,
  "rules": [
    {"kind": "ip",     "value": "1.2.3.4",    "direction": "out"},
    {"kind": "cidr",   "value": "10.0.0.0/8", "direction": "out"},
    {"kind": "domain", "value": "example.com"}
  ]
}
```

关键点：**`kind: "domain"` 的条目不走防火墙**，而是进代理的域名列表。
一个文件同时描述两类规则，执行时按 `kind` 分派——这样家长不用理解
"为什么有的域名规则在这里、有的在那里"。

### 5.3 GUI 增删的前提

控制台目前**只读**（`host/ui/server.py`，`docs/host-layer.md` §2.10）。
要支持规则增删，需要先做 `docs/roadmap.md` 阶段 2.1（写操作框架 + CSRF + 审计日志）。

**顺序不能反**：先有写框架，再有规则编辑页。否则会得到一个绕过审计的
第二条写路径——那正是 §2.10 当初拒绝 POST 的理由。

## 6. 结论与建议

### 6.1 对问题 1 的回答

**要，但要区分两类规则：**

| 规则类型 | 谁执行 | 优先级 |
|---|---|---|
| **按 IP / 网段** | 防火墙（`host/firewall.py`） | 中 |
| **按域名** | 代理（`host/proxy/`），不是防火墙 | **高**（见 roadmap 阶段 1） |

理由：防火墙看不见域名，强行按 IP 拦域名在 CDN 时代基本无效。
域名拦截必须走代理。

规则文件用 JSON，`kind` 字段分派，一个文件描述两类。
GUI 增删依赖 roadmap 阶段 2.1 的写框架，**不能提前**。

### 6.2 对问题 2 的回答

**不要用防火墙做主时间控制，但"全网断网"需要防火墙。**

| 层级 | 机制 | 覆盖 | 状态 |
|---|---|---|---|
| 软时间控制 | `filter` 短路 | 走代理的应用 | 引擎 DONE，**宿主未接线** |
| 硬时间控制 | 防火墙 `0.0.0.0/0` | 全部 | 设计未定 |

顺序：**先把软控制接线**（成本低、可测、覆盖主要场景），
再评估硬控制。硬控制的三个前提问题（§4.5）必须先有答案，
尤其是"服务崩溃后规则残留导致永久断网"。

时钟防篡改**不用 NTP**，改用收回 `SeSystemtimePrivilege` + 单调时钟锚定，
两者都不需要网络，与离线约束一致。

### 6.3 对路线图的影响

本文不改变阶段顺序，但给阶段 1 增加了具体内容：

| 原任务 | 补充 |
